## Overview

Enable multiple terminal sessions where commands execute on the user's active (selected) session, allowing long-running CLI processes to run alongside other commands.

## Phases

### Phase 21: Backend Session Foundation

**Goal**: Backend can manage multiple terminal sessions with isolated PTYs, and long-running processes persist across session switches.

**Depends on**: v2.0 Terminal Integration (phases 16-20 complete)

**Requirements**: SESS-01, SESS-04, SESS-05, EXEC-04

**Plans**: 3 plans

Plans:
- [x] 21-01: Session types, struct refactoring, CRUD API (CreateSession, ListSessions, CloseSession, RenameSession, active session)
- [x] 21-02: Per-session PTY lifecycle, namespaced events, ServiceStartup/Shutdown
- [x] 21-03: Frontend event wiring, Wails bindings, multi-session Go tests (19 tests with race detector)

**Details**:
Introduced SessionInfo (5 exported fields, camelCase JSON) and unexported sessionState (15+ internal per-PTY fields) with `sync.RWMutex` for the sessions map and per-session `sync.Mutex`. UUID v4 session IDs via `github.com/google/uuid`. Per-session PTY lifecycle with namespaced Wails events (`pty-output:{id}`, `pty-exit:{id}`, `pty-cleared:{id}`). 19 Go tests (10 updated, 9 new) covering multi-session CRUD, process persistence across switches, output isolation, and concurrency via race detector.

### Phase 23: Frontend Tabbed Terminal

**Goal**: Users can manage and interact with multiple terminal sessions through a tabbed interface with full keyboard and mouse support.

**Depends on**: Phase 21, Phase 22

**Requirements**: SESS-02, SESS-03, SESS-06, UI-01, UI-02, UI-03, UI-04, UI-05, UI-06

**Plans**: 3 plans

Plans:
- [x] 23-01: TerminalTabBar component with drag-and-drop reorder, right-click context menu, status indicators, SessionInfo type, CSS
- [x] 23-02: App.tsx session state management, multi-mount TerminalComponents, TerminalTabBar wiring, clear/copy button refactor
- [x] 23-03: Keyboard shortcuts with focus-dependent dispatch (Ctrl+T/W/Tab/Shift+Tab) for terminal vs command tabs

**Details**:
TerminalTabBar uses `dnd-kit` PointerSensor with `activationConstraint distance:5` to prevent click/drag interference; separate GripVertical drag handle with attributes/listeners on handle (not tab div). Status dot uses CSS modifiers with `var()` color references. Context menu via shadcn `ContextMenu` primitives. Multi-instance TerminalComponent mounting with `key={session.id}` and CSS `display:none` for inactive (same pattern as Phase 14 CommandDetailTab). Per-session TerminalHandle ref map. Focus-dependent shortcut dispatch via `isFocusInTerminalPane()` checking `document.activeElement.closest()` against `.terminal-pane` and `.xterm-helper-textarea`.

## Milestone Summary

**Phases with no plans (scoped out):**
- Phase 22: Database Persistence — scoped out during Phase 25. Persistence deferred to v2.

**Key Decisions:**

- **Phase 21**: `sync.RWMutex` for sessions map (Lock for writes, RLock for reads); internal unexported `sessionState` with per-session `sync.Mutex`; public exported `SessionInfo` with `json:"camelCase"` tags
- **Phase 21**: `unlock-before-blocking` deadlock prevention (`ss.mu.Unlock` before PTY close/wait); snapshot-then-iterate pattern for shutdown
- **Phase 23**: `dnd-kit` with `PointerSensor activationConstraint distance:5` to prevent click/drag interference; attributes/listeners on GripVertical handle (not tab div)
- **Phase 23**: Multi-instance mounting via `key={session.id}` + CSS `display:none` for inactive (reuses Phase 14 CommandDetailTab pattern)
- **Phase 24**: Direct in-process service-to-service dispatch via package-level singleton (`terminalSvc`) — no event hop
- **Phase 25**: Build-tagged `ptyBackend` interface seam (`!windows` and `windows` files implement same interface, platform-portable code in non-tagged file) — D-11/D-12. Enables real orchestration tests against mock on darwin and cross-compile verification on Windows
- **Phase 25**: `getWorkingDir()` mirrors `execution_service.go:resolveWorkingDir` (same log format, same OS-keyed read, same home fallback) — visual parallelism makes the contract recognizable
- **Phase 25**: `MaxSessions = 10` resource-exhaustion guard (rationale: unbounded session creation could leak FDs/goroutines)
- **Phase 25 D-02/D-03**: In-memory scope chosen for v2.1; PERS-01..PERS-04 deferred to v2 (rationale: deliver the multi-session UX now, persistence is a separable concern)

**Issues Resolved:**

- OutputPane orphan code removed (280-line component + ~170 lines CSS + i18n keys + e2e selectors)
- Race condition in PTY cleanup during shutdown (snapshot-then-iterate)
- Click/drag interference in TerminalTabBar (PointerSensor activationConstraint)
- Stale closure in keyboard shortcut focus detection (useCallback with empty deps, reads `document.activeElement` at call time)
- Click vs shortcut conflict for Ctrl+T/W/Tab (focus-dependent dispatch)
- Goroutine leak risk from unbounded session creation (MaxSessions guard)

**Issues Deferred:**

- **PERS-01..PERS-04**: Session persistence across app restarts (name, working dir, shell, active session restore) — deferred to v2
- **PERS-05**: Session scrollback history persisted across restarts
- **PERS-06**: Shell command history persisted per session
- **SESS-07**: Duplicate a session (clone working dir, env, history)
- **SESS-08**: Split terminal pane horizontally/vertically (tmux-style)
- **SESS-09**: Broadcast input to multiple sessions simultaneously
- **SESS-10**: Export session layout as workspace file
- **SESS-11**: Share session output via link (read-only)

**Windows conpty runtime gap (documented):**

- `pty_backend_windows.go` is a stub that returns "not implemented" errors from Start/Resize
- `GOOS=windows go build ./...` cross-compile verification passes
- Runtime conpty testing is not done in this milestone
- Future work: replace stub with real conpty implementation, add `windows-latest` CI runner
- See `.planning/phases/25-polish-integration/CHECKPOINT.md` and `AGENTS.md` Windows conpty verification gap section

**Technical Debt Incurred:**

- `getWorkingDir()` and `execution_service.go:resolveWorkingDir` are parallel implementations of the same contract (no shared helper) — refactor candidate if a third caller appears
- Mock PTY backend is darwin-only (`//go:build darwin`) — orchestration tests do not run on linux/windows CI yet
